# Sync Gateway Public API Tests (port 4984)

Quick tests against the lab's Sync Gateway public REST API, verifying the server is up, the `labdb` database is online, and channel-based access control is working as configured in `sync_gateway.json`.

> Run `curl http://localhost:4985/_all_dbs` first (the **Admin** API on **4985**, not 4984) to confirm the actual configured database name and that it's actually loaded — substitute it for `labdb` everywhere below if it differs. Sync Gateway 2.1's Admin API has no auth requirement by default, so this is the most unambiguous way to check database status; see the note at the end of Test 2 for why the public API alone can be misleading here.

## Tests

**1. Gateway is up and reports version 2.1**
```bash
curl http://localhost:4984/
```
Expected:
```json
{"couchdb":"Welcome","vendor":{"name":"Couchbase Sync Gateway","version":"2.1"}, ...}
```

**2. Database is online**
```bash
curl -u alice:letmein1 http://localhost:4984/labdb/
```
Expected:
```json
{"db_name":"labdb", ...}
```

> **Read carefully before treating this as a failure:** because this lab's config disables `GUEST` access, an *unauthenticated* request to `/labdb/` correctly returns `401 {"error":"Unauthorized","reason":"Login required"}` — **that response means the database IS online** and access control is working as intended, not that something is broken. A genuinely missing/unloaded database instead returns `404 {"error":"not_found","reason":"no such database \"labdb\""}`. These two errors look similar at a glance but mean opposite things — check the error `reason` text, not just the fact that an error occurred. If you want an authentication-independent check, use the Admin API instead: `curl http://localhost:4985/labdb/`.

**3. alice can read a document she owns**
```bash
curl -u alice:letmein1 http://localhost:4984/labdb/device::001
```
Expected: the full `device::001` JSON document.

**4. alice CANNOT read bob's document — proves channel-based access control**
```bash
curl -i -u alice:letmein1 http://localhost:4984/labdb/device::003
```
Expected: `HTTP/1.1 403 Forbidden`

**5. bob CAN read his own**
```bash
curl -u bob:letmein2 http://localhost:4984/labdb/device::003
```

**6. Write a new document as alice, into her own channel**
```bash
curl -u alice:letmein1 -X PUT http://localhost:4984/labdb/device::006 \
  -H "Content-Type: application/json" \
  -d '{"type":"device","deviceId":"006","owner":"alice","model":"sensor-D","status":"active"}'
```
Expected:
```json
{"id":"device::006","ok":true,"rev":"1-..."}
```

**7. Read it back**
```bash
curl -u alice:letmein1 http://localhost:4984/labdb/device::006
```

**8. Changes feed for alice's channel (what a Couchbase Lite client would pull)**
```bash
curl -u alice:letmein1 "http://localhost:4984/labdb/_changes?feed=normal"
```

**9. Unauthenticated request — no credentials at all (GUEST is disabled)**
```bash
curl -i http://localhost:4984/labdb/device::001
```
Expected: `HTTP/1.1 401 Unauthorized` with `{"error":"Unauthorized","reason":"Login required"}` — same distinction as Test 2: this specific error text confirms the database exists and is correctly rejecting anonymous access, it isn't a failure.

Tests 4 and 9 are the ones actually worth watching closely — they prove the sync function's `channel(doc.owner)` / `access(doc.owner, doc.owner)` logic is enforcing per-owner isolation, not just that the server responds.

## Troubleshooting: database not coming online

If `curl http://localhost:4985/_all_dbs` returns `[]` (empty) or shows a database name you don't recognize (e.g. `["db"]`, Sync Gateway's built-in in-memory example database) instead of `["labdb"]`, the real config file isn't being loaded. On this lab's specific setup, the root cause turned out **not** to be anything in the JSON config content — it was that Sync Gateway's config file **lives in a different location than Sync Gateway's own general documentation implies**.

**What we found, for this specific RPM install:** this Sync Gateway 2.1 RPM installs an old-style SysV init script rather than a native systemd unit — `systemctl cat sync_gateway` shows a generated shim (`Automatically generated by systemd-sysv-generator`), not a real unit file, because the actual logic lives in `/etc/rc.d/init.d/sync_gateway`. That script hardcodes:
```
CONFIG=/opt/sync_gateway/etc/sync_gateway.json
```
— not `/home/sync_gateway/sync_gateway.json`, the path shown in most general Sync Gateway installation documentation. There is also **no `/etc/sysconfig/sync_gateway` override support** in this script (an earlier attempt to fix this via that mechanism was a dead end — it's simply never sourced). The provisioning script now writes directly to the correct hardcoded path, but if you're troubleshooting a fresh symptom, don't assume the documented default path is where this install actually reads from.

**Diagnostic steps, most direct first:**

1. **See the config path the running process was actually launched with** — this sidesteps needing to read/interpret the init script at all:
   ```bash
   ps -ef | grep sync_gateway | grep -v grep
   ```
   The last argument on the `sync_gateway` binary's command line is the config file it loaded. Confirm that path is the one you actually edited.

2. **If you need to find the mechanism from scratch on a different install**, read the actual init script rather than assuming a convention:
   ```bash
   sudo cat /etc/rc.d/init.d/sync_gateway
   ```
   Look for the `CONFIG=` assignment near the top, and check whether it sources any override file (`. /etc/sysconfig/...` or similar) before using it.

3. **Check recent log activity** — this init script logs to `/var/log/sync_gateway/`, and process start/stop events also show in `journalctl`, but note `journalctl -u sync_gateway` mostly just reflects "did the process fork," not Sync Gateway's own internal logging:
   ```bash
   journalctl -u sync_gateway -n 60 --no-pager
   sudo tail -60 /var/log/sync_gateway/sync_gateway_error.log
   ```

4. **Confirm the config file is valid JSON** (the `sync` function's backtick-delimited string is a Sync Gateway extension, not standard JSON, so a `json.tool` failure specifically inside that block is expected and not meaningful — but a failure elsewhere in the file is real):
   ```bash
   cat /opt/sync_gateway/etc/sync_gateway.json
   ```

5. **Confirm the RBAC user Sync Gateway connects as can actually reach the bucket:**
   ```bash
   curl -u sync_gateway:sgpassword123 http://localhost:8091/pools/default/buckets/labdb
   ```
   A `401`/`403` here means the credentials in the config don't match what Couchbase Server actually has provisioned for that user — re-check against what `couchbase-cli user-manage` set.

6. **After any fix, restart and check the Admin API, not the public one** (see the note on Test 2 for why):
   ```bash
   systemctl restart sync_gateway
   sleep 5
   curl http://localhost:4985/_all_dbs
   ```
